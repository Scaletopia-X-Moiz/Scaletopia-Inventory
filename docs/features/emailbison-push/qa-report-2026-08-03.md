# EmailBison push — full UI QA pass (2026-08-03)

Manual end-to-end test of the "Add to EmailBison" and "Add to Campaign" features, run against
the **live production app** (`https://inventory.scaletopia.io`), using the `Internal` client's
dedicated EmailBison test-workspace credentials. Four parallel test passes were run via Chrome
browser automation, each in its own tab, covering:

1. `/people` — plain push to workspace (real leads created)
2. `/companies` — plain push to workspace (real leads created)
3. `/people` + `/companies` — "Add to Campaign" flow (real campaign-attach)
4. Edge cases / validation on `/people` (no real pushes)

No real client's EmailBison workspace was touched — every real push in this pass went to the
`Internal` test client (`https://send.scaletopia.io`, dedicated test-account token, per
`docs/features/ghl-push/` sibling QA session's credential setup).

## Other observations (not filed as issues)

- The exact outgoing wire payload for `existing_lead_behavior` (`patch`/`put`) and custom variables
  was not independently confirmed at the network level during this pass — `read_network_requests`
  only exposes method/URL/status, not bodies. The UI states going into each push were correct and
  the pushes succeeded with the expected create/update counts, but a wire-level check (e.g. via a
  proxy or JS fetch interception) would be needed to fully close the loop on
  `docs/features/emailbison-push/api-research.md`'s still-open question about the exact request/
  response shape.

## Scope not covered

- Did not test with a client that has no EmailBison campaigns at all (Internal's test workspace
  currently has exactly one real campaign, "Testing Spintax" id 949) — the empty-campaign-list
  state is unverified.
- Did not attempt a push against a client whose token has been revoked/is invalid (error-path for
  a bad-but-present credential, as opposed to a missing one) — the "no credentials" disabled state
  was verified, but not the "credentials present but rejected by EmailBison" path.
